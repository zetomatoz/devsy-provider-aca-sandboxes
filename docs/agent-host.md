# Remote agents in the workspace

Devsy provisions the development environment. VS Code's Agent Host runs agent
harnesses inside that environment. These are separate components: a successful
Devsy workspace does not by itself prove that a model-backed agent session ran.

## Connect the Agents window

1. Start the workspace with this provider and keep it running.
2. Verify the SSH entry generated by Devsy:

   ```sh
   ssh -G YOUR_WORKSPACE.devsy | rg '^(hostname|user|port|proxycommand) '
   ssh YOUR_WORKSPACE.devsy 'pwd; dotnet --version'
   ```

3. Run `./scripts/open-agents.sh YOUR_WORKSPACE` on your computer. The script
   opens the Agents window and prints the SSH alias to select.
4. In the new session, choose **Workspace → Remote → SSH**, then select
   `YOUR_WORKSPACE.devsy`. Enter the remote folder (for the example,
   `/workspaces/dotnet-aca/`).
5. Choose an available harness, authenticate if requested, and submit a bounded
   task such as: "Run `./smoke.sh` in the .NET sample's root directory. Report
   the result without changing any source files."

VS Code installs its remote CLI when required. The source machine needs outbound
access to the relevant VS Code downloads and the selected model service. The
Agents window's connection is independent of a normal editor window.

The installed macOS VS Code 1.139.1 was inspected during development: its CLI
supports `--agents` and `agent host`, and its remote Agent Host implementation
recognizes SSH `ProxyCommand`. Its bundled code passes the proxy's byte stream to
the SSH client. The corresponding [official implementation](https://github.com/microsoft/vscode/blob/main/src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts)
can change between releases. A working OpenSSH command is the first check; the
Agents window then uses its own SSH client and launches a dedicated Agent Host
in the container.

The local CLI can also be called directly on macOS:

```sh
"/Applications/Visual Studio Code.app/Contents/Resources/app/bin/code" --agents
```

The helper uses `VSCODE_CLI` if set, then `code` on `PATH`, then that macOS path.
It does not assume an undocumented CLI flag can select the remote environment or
submit an agent task automatically.

See [VS Code remote agent sessions](https://code.visualstudio.com/docs/agents/run/remote-agent-sessions)
for the current connection UI. Connecting directly to the Devsy workspace runs
the agent there. There is no need to select **Use Dev Container** a second time:
that action creates another container and requires Docker on the selected host.

## Optional standalone host

Inside the development environment, once the VS Code CLI is installed:

```sh
code agent host
```

The host binds to localhost and uses a connection token by default. Leave those
defaults intact. `code agent endpoints` returns sensitive connection credentials;
do not paste its output in logs or issues.

`code agent host --tunnel --name devsy-aca` offers an alternative authenticated
dev-tunnel route. It requires its own sign-in and a permitted external relay.
It is optional: the provider transport is intended to use Azure Sandbox APIs.
See [Agent Host architecture](https://code.visualstudio.com/docs/agents/concepts/agent-host).

## Optional self-hosted model

A model endpoint was not supplied with this project. The following are
configuration examples, not evidence of a completed model inference.

For a quick **Copilot CLI** experiment inside the workspace, use an endpoint
reachable from the remote environment, with tool calling and streaming support:

```sh
export COPILOT_PROVIDER_TYPE=openai
export COPILOT_PROVIDER_BASE_URL=https://YOUR_MODEL_HOST/v1
export COPILOT_MODEL=YOUR_MODEL_ID
# Set COPILOT_PROVIDER_API_KEY securely in this shell if the endpoint requires it.
export COPILOT_OFFLINE=true
copilot
```

`localhost` in this shell means the remote container, not your laptop. Offline
mode restricts Copilot CLI to its configured provider; your endpoint still needs
to be reachable. A populated `~/.copilot/providers.json` takes precedence over
the legacy environment configuration above. The current persistent format is:

```json
{
  "providers": [
    { "name": "corporate", "type": "openai", "baseUrl": "https://YOUR_MODEL_HOST/v1" }
  ],
  "models": [
    { "id": "YOUR_MODEL_ID", "provider": "corporate", "maxPromptTokens": 32768, "maxOutputTokens": 4096 }
  ]
}
```

Set the limits to the actual model's supported limits. Add credentials only to a
private configuration file, never a committed example. See GitHub's
[Copilot CLI model setup](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-llm-models)
and [BYOK environment setup](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/use-byok-models).

For the **VS Code Agents window**, enable experimental
`chat.agentHost.byokModels.enabled`, then open **Chat: Manage Language Models**
and add a **Custom Endpoint**. Choose the endpoint's API type and enable tool
calling for a capable model. Harnesses have separate authentication/configuration
requirements; configuring a model in the VS Code picker is not a universal
configuration for every CLI. See [VS Code model configuration](https://code.visualstudio.com/docs/agent-customization/language-models).

Corporate policies and endpoint reachability still apply. Keep model credentials
out of the provider manifest, source control, and connection-command output.
